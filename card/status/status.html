Conceito fundamental

O que é
Status Code?

O Status Code é um código numérico enviado pelo servidor para informar o resultado de uma requisição HTTP. Ele permite que aplicações e profissionais de QA entendam rapidamente se uma operação foi concluída, redirecionada ou encontrou algum tipo de erro.

CONCEITO / 01 HTTP

Status Code HTTP response

É o código numérico retornado pelo servidor após uma requisição HTTP. Ele representa o resultado daquela operação e ajuda o cliente a entender como a requisição foi processada.

CONCEITO / 02 3 DÍGITOS

Como interpretar? classification

O primeiro número indica a categoria da resposta. Códigos iniciados por 2 representam sucesso, 3 redirecionamentos, 4 erros relacionados à requisição e 5 problemas no processamento do servidor.

CONCEITO / 03 RESPONSE

Onde aparece? API response

O Status Code faz parte da resposta HTTP. Ao testar uma API, ferramentas como Postman, Insomnia ou automações de teste exibem o código junto com os demais dados retornados pelo servidor.

CONCEITO / 04 QA

Por que o QA testa? validation

Porque o código deve representar o resultado esperado da operação. Um teste de API não deve verificar apenas os dados retornados, mas também se o Status Code está correto para cada cenário.

Categorias dos Status Codes
1xx

Informacional

A requisição foi recebida e o processamento continua.

2xx

Sucesso

A requisição foi recebida e processada com sucesso.

3xx

Redirecionamento

É necessário realizar uma ação adicional para concluir a operação.

4xx

Erro do cliente

A requisição possui algum problema ou não pode ser atendida.

5xx

Erro do servidor

O servidor encontrou um problema ao processar a requisição.

200 SUCCESS

OK

A requisição foi processada com sucesso. É um dos códigos mais comuns em APIs, especialmente em operações de consulta realizadas com GET.

GET /usuarios/123 → 200 OK
201 CREATED

Created

Indica que um novo recurso foi criado com sucesso. É comum em respostas de operações POST que criam registros.

POST /usuarios → 201 Created
204 NO CONTENT

No Content

A requisição foi processada com sucesso, mas a resposta não possui conteúdo no corpo. É comum em operações de atualização ou exclusão.

DELETE /usuarios/123 → 204
400 CLIENT ERROR

Bad Request

A requisição não pôde ser processada porque possui dados inválidos, parâmetros incorretos ou uma estrutura que não atende ao esperado pela API.

POST /usuarios → 400 Bad Request
401 AUTHENTICATION

Unauthorized

A requisição não possui uma autenticação válida. Pode ocorrer quando o token está ausente, inválido ou expirado.

GET /perfil → 401 Unauthorized
403 AUTHORIZATION

Forbidden

O servidor entendeu a requisição, mas o usuário autenticado não possui permissão para executar aquela operação.

DELETE /usuarios/123 → 403 Forbidden
404 NOT FOUND

Not Found

O recurso solicitado não foi encontrado. Pode acontecer quando uma URL ou identificador não corresponde a um recurso existente.

GET /usuarios/999 → 404 Not Found
409 CONFLICT

Conflict

A requisição não pode ser concluída devido a um conflito com o estado atual do recurso. É comum em regras de negócio que impedem operações duplicadas.

POST /usuarios → 409 Conflict
422 VALIDATION

Unprocessable Content

A requisição está bem formada, mas os dados enviados não podem ser processados por causa de regras de validação ou conteúdo semanticamente inválido.

POST /usuarios → 422
500 SERVER ERROR

Internal Server Error

O servidor encontrou uma condição inesperada que impediu o processamento da requisição. Normalmente indica um problema interno da aplicação.

GET /usuarios → 500 Internal Server Error
502 GATEWAY

Bad Gateway

Um servidor que atua como gateway ou proxy recebeu uma resposta inválida de outro servidor ao tentar processar a requisição.

GET /pagamentos → 502 Bad Gateway
503 UNAVAILABLE

Service Unavailable

O servidor não está disponível para processar a requisição, geralmente por indisponibilidade temporária, manutenção ou sobrecarga.

GET /usuarios → 503 Service Unavailable
QA / API Validation

O que o QA deve validar?

Ao testar uma API, o Status Code deve fazer sentido para o cenário executado. O QA deve validar não apenas o sucesso, mas também o comportamento da API diante de entradas inválidas, ausência de autenticação, falta de permissão, recursos inexistentes e falhas internas.

STATUS O código retornado corresponde ao resultado esperado?
BODY O corpo da resposta contém os dados ou mensagem esperados?
HEADERS Os cabeçalhos necessários estão presentes e corretos?
NEGATIVE A API trata corretamente entradas inválidas e cenários de erro?
SECURITY Autenticação e autorização estão sendo aplicadas corretamente?
